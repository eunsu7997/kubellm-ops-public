# 3분 발표와 예상 질문

## 0:00 — 해결하려는 문제

“개인 RTX 4060 한 장에서 LLM 요청이 몰릴 때, 요청을 무조건 보내는 대신 자원과 점유를 확인하고 유입을 제한하며 결과를 근거로 설명하는 실험입니다. 다섯 프로젝트의 일부 실제 코드를 하나의 실행 흐름으로 연결했습니다.”

## 0:30 — 실행 흐름

“GPUDeploy Guard가 기존 Deployment의 자원과 probe를 정적으로 검사합니다. gpu-queue-lab은 실제 batch 점유를 조회합니다. 안전 조건이 충족돼야 KubeLLM-Ops가 기존 Gateway와 Qwen 모델로 실제 SSE를 실행합니다. llm-slo-lab의 고정된 지표 코드를 가져와 오류율과 전체 응답 지연을 판정합니다.”

## 1:10 — 결과 화면

OPEN-ME.html은 반드시 ‘10월 22일 집 GPU에서 실행한 기록’이라고 소개한다.

“이 실행에서는 기준 요청 40개 중 30개가 완료되고 10개는 admission 단계에서 429로 거절됐습니다. 실패가 모두 명시적인 429이고 수락 후 실패가 없어서, 별도 실험 경로에만 최대 두 번의 제한 재시도를 선택했습니다. 이후 40개가 모두 완료됐고 전체 SSE 완료 P99는 약 1.34초였습니다. 재시도 대기까지 포함한 수치입니다.”

“성공률이 나아지는 대신 대기와 HTTP 시도가 증가합니다. 이전 정책별 160개 비교에서는 1초 TTFT 달성률이 두 정책 모두 75%였습니다. 따라서 모든 지표가 좋아졌다고 주장하지 않습니다.”

## 2:00 — 실패도 설명

“Incident Copilot은 근거를 모으고 실제 Qwen 초안을 검증합니다. 이번 초안은 불확실성 표현 조건을 충족하지 않아 채택하지 않았고 근거 리포트로 대체했습니다. LLM의 제안이 명령으로 실행되지는 않습니다.”

## 2:30 — 범위와 다음 단계

“현재는 단일 GPU에서 정해진 부하로 재현한 로컬 제어 실험입니다. Kubernetes GPU 배포나 다중 GPU 확장은 실행하지 않았습니다. 다음은 별도 계획으로 장시간 안정성과 다른 부하에서도 재현되는지 검증하는 것입니다. 발표를 위해 검증되지 않은 확장 성과를 넣지는 않았습니다.”

## 예상 질문

- 왜 5개인가? 배포 전 검사, batch 점유, 실제 추론·유입 제어, 지표 판정, 장애 근거라는 역할을 연결했다. 5개의 독립 production 서비스를 운영한 것은 아니다.
- 왜 P99 2.5초인가? 운영 계약이 아닌 실행 전에 고정한 실험용 목표다. 40개 표본의 P99는 꼬리 추정이 거칠어 장기간 보장으로 해석하지 않는다.
- 429는 모델 장애인가? 이 실험에서는 큐·토큰 예산에 따라 요청 수락 전에 명시적으로 거절한 결과다. 최종 429도 SLO 오류율에 포함했다.
- 재시도가 중복 생성하지 않나? 명시적인 429만 최대 두 번 시도하며, 수락된 200·부분 SSE·5xx·전송 오류는 자동 재생하지 않는다.
- GPU 메모리를 늘렸나? 아니다. 기존 모델·컨테이너 설정을 유지하고 별도 localhost 어댑터에서 비교했다.
- Copilot이 실패했는데 괜찮나? 초안 품질은 미달했으며, 검증기가 채택을 차단한 경계를 확인했다. 생성 품질 개선은 남은 작업이다.
- 학원 연결이 안 되면? 저장된 결과 화면을 기록이라고 명시해 발표한다. 실시간 성공이라고 말하지 않는다.
- 현재 구현의 한계는? 고정된 작은 모델과 제한된 trace, 순차 정책 실행, 단일 GPU다. retry 효과를 GPU 과부하 보호 효과나 일반적인 인과적 성능 향상으로 확대하지 않는다.

## 현장 순서

1. 준비한 ZIP을 풀고 OPEN-ME.html을 연다. 인터넷 없이 기록 발표가 가능하다.
2. 시간이 되면 같은 개인 tailnet에서 ready → 실제 채팅 → SSE content와 DONE을 확인한다.
3. 추가 실험을 실행할 수 있는 집 PC 원격 제어는 별도 미설정이다. 발표 직전에 공개 포트를 열거나 실험 환경을 바꾸지 않는다.
